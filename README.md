「记一笔」是一个**个人自用、从零手写**的记账应用：Kotlin + Jetpack Compose，没有用任何图表库、图片库或 UI 模板。
它想解决的核心问题很具体 —— **记账最容易死在第 3 天，因为"付完钱还要再手动输一遍"**。所以这个项目把大部分工程量都花在了「自动记账」上：支付通知、无障碍读屏、AI 兜底三条链路互补，付完钱账目自己落库，还会弹一条横幅让你当场核对。

> **文档说明**：本文件描述的是**当前代码的真实实现**。历史上出现过的夸大描述（小票 OCR、桌面小组件、Vico 图表库、Coil 图片加载等从未落地或已删除的能力）已在 2026-10 重构中一并修正，详见 [重构记录.md](重构记录.md)；本文件里的机制与常量均来自源码，不是设计稿。

## 自动记账怎么工作

### 三条链路

```
                    ┌──────────────────────────────────────────┐
   你在微信/支付宝   │  ① 通知链路（主力，前后台都能抓）          │
   完成一笔支付  ──┼─▶ NotificationListenerService            │
                    │     └─ 规则表解析 ──▶ 未命中 ──▶ AI 兜底  │
                    └──────────────────────────────────────────┘
                                   │
                    ┌──────────────┴───────────────────────────┐
                    │  ② 无障碍链路（补通知的盲区）              │
                    │     你在 App 内付款时系统不推通知，        │
                    │     所以读"支付成功页"的屏幕文字           │
                    └──────────────────────────────────────────┘
                                   │
                                   ▼
                    ┌──────────────────────────────────────────┐
                    │  ③ 统一落库 PaymentRecorder               │
                    │     开关 → 三层去重 → 匹配账户 → AI 内容   │
                    │     审核 → 猜分类 → 写交易 → 同步余额 →    │
                    │     横幅提醒（点开直接编辑）               │
                    └──────────────────────────────────────────┘
```

### ① 通知链路

`NotificationListenerService` 只监听 **微信（`com.tencent.mm`）与支付宝（`com.eg.android.AlipayGphone`）** 两个包，其他通知一概不看。

- **文案读取有讲究**：支付通知基本都是 `BigTextStyle` / `InboxStyle`，此时 `EXTRA_TEXT` 只是被截断的短句，**金额藏在 `EXTRA_BIG_TEXT` 里**。所以按 `BigText > TextLines > Text` 的优先级取，再把常见的 `EXTRA_SUB_TEXT`（"已支付"这类方向词）拼进正文提高命中率。
- **规则优先**：本地规则表（包名白名单 + 有序规则 + 三段式金额提取）先跑，命中即入库。
- **AI 兜底**：只有「规则未命中 + 不是聊天会话（用 `MessagingStyle` 的 `EXTRA_MESSAGES` 判定）+ 文案看起来像支付」三者同时成立才会问模型，并且**节流 10 秒一次**——费额度也费电，营销群发文案本来也不是 AI 能救的。
- 聊天通知直接跳过：微信消息用 `MessagingStyle` 发系统通知，这是系统级标记，比文本启发可靠得多。

### ② 无障碍链路（补盲区）

**你在微信 / 支付宝里主动付款（扫码、转账）时，系统不会给正在前台使用的 App 推通知**，通知链路天生抓不到。这条链路就是补这个洞：在支付成功页面出现的那一刻读取屏幕文字。

防误读的设计是「宁漏勿错」：

- 事件订阅被配置 XML **限定为两个包的 `typeWindowStateChanged` / `typeWindowContentChanged` 两类事件**，点击 / 滚动 / 手势一概不订阅；
- 窗口类名做**三态分类**（`PaymentWindowHints`）：命中支付语义（`pay` / `trans` / `cashier` / `remit` …）→ 刷新放行窗口并读屏；命中明确无关页（聊天主页、扫一扫取景）→ 立刻关闭放行窗口；弹窗 / 通用容器 / 混淆类名（`dialog.k2`、`UIPageFragmentActivity`）→ **不关窗口**，因为真实支付链路常常经过这些类名不含支付语义的页面；
- 解析仍走完整规则：没有「支付成功 / 已转账给」这类方向词 + 金额，一律不记 —— 翻聊天记录看到旧转账文案不会误记账。

硬性参数（都在 `PaymentAccessibilityService` 的 companion object 里）：读屏延迟 **600 ms**（窗口切换瞬间 `rootInActiveWindow` 还指着旧窗口）、内容变化最小间隔 **500 ms**、支付放行窗口 **30 s**、节点数上限 **300**、窗口文本节流 **3 s**。遍历节点树是几百次跨进程 Binder 调用，所以**全部丢到 `limitedParallelism(1)` 的后台作用域**，主线程零重活。

### ③ 统一落库与去重

两条链路共用同一个 `PaymentRecorder`，所以不会重复记账。去重是**三层**：

| 层 | 机制 | 参数 |
|---|---|---|
| 事件指纹 | 进程内 LRU（`LinkedHashMap`），有 id 才判 | TTL **10 分钟**、上限 **200 条**；通知用 `通知key + 内容hash`，无障碍用 `a11y:包名:整屏文本` |
| 金额时间窗 | 同金额同类型在时间窗内视为同一笔 | **±30 秒** |
| 互斥锁 + 落库前复查 | `recordMutex` 串行化「查库 → 插库」，锁内再复查一次金额窗 | 落库失败会回滚指纹 |

### ④ AI 内容审核（只针对读屏链路）

无障碍读到的是**整屏窗口文字**（用户可能正停在聊天页或商品页），本地规则只能判断"屏里出现了支付语义词"。所以当**商户名为空、或原文超过 30 字**时，会把这屏交给模型复核「这是不是一笔已完成的收付款」，并让它给出干净备注。

- **审核超时 8 秒**（`withTimeoutOrNull`），慢网络不会拖住落库与横幅；注意这是**审核这一层的上限**，底层 OkHttp 读超时是 20 s；
- 审核否决 → 不记账，但原文进「未识别队列」，不静默丢弃；
- 没有配置 AI 时行为与从前一致，规则链路完全不受影响。

### ⑤ 三个贴心的收尾

- **账户自动匹配**：按支付方式与卡尾号猜账户（卡尾号命中账户名 → 账户名含支付方式 → 「零钱通」退化匹配「零钱」→ 按账户类型映射且同类型唯一才用），**全落空才回退默认账户** —— 宁落默认，也不错配。
- **分类学习**：你手动纠正某笔自动记账的分类后，记住「商户 → 分类」，下次同商户直接采用；归一化后最多存 **200 条**，可在「自动记账」页一键重置。
- **未识别队列**：没解析出来的支付通知原文留在应用内可见（最多 20 条），方便按真机文案补规则，而不是静默丢弃。

## 能识别什么、识别不了什么

| 场景 | 通知链路 | 无障碍链路 |
|---|---|---|
| 微信 / 支付宝扫码付款（前台） | — | ✅ 主要覆盖 |
| 微信 / 支付宝转账 | ✅ | ✅ |
| 后台收到支付结果通知 | ✅ | — |
| 小程序内支付（`AppBrandUI`） | 视是否推通知 | ❌ **已知漏记**：小程序窗口不在支付窗口白名单内 |
| 自定义控件渲染金额的页面 | 视是否推通知 | ❌ **已知漏记** |
| 银行卡短信 / 其他银行 App | ❌ 不支持（只白名单了微信与支付宝） | ❌ 不支持 |

漏记的那些**可以在「自动记账」页手动补一笔**。这个取舍是刻意的：宁可漏一笔让用户补，也不能把浏览页面误记成账。

## 权限与后台保活（重要）

> 这一节是「为什么我付了钱却没记账」的标准答案，**装完一定要配**。

自动记账依赖两项**不是运行时权限**的授权，只能由用户在系统设置里手动开启：

| 授权 | 作用 | 开启路径 |
|---|---|---|
| **通知使用权** | 抓微信 / 支付宝的支付通知 | 设置 → 通知 → 通知使用权 → 记一笔 |
| **无障碍服务** | 抓扫码 / 转账等**前台支付**（系统此时不推通知） | 设置 → 无障碍 → 记一笔 · 支付页面识别 |

### 为什么它们会「自己关掉」

Android 在**强停应用**时会关闭该应用的无障碍服务与通知监听 —— 而国产 ROM 的「清理后台」、把最近任务卡片划掉，做的就是强停。**系统不会提醒用户**，现象就是"付了钱却没记账"，往往过几天才发现。

真机实测（Redmi / Android 14）：

| 触发 | 无障碍服务 | 通知使用权 |
|---|---|---|
| **强停**（清理后台 / 划掉最近任务卡片） | ❌ 系统**直接把服务从列表里删掉**，必须手动重开 | ✅ 通常不受影响，不必重开 |
| **覆盖安装 / 应用更新** | ⚠️ 随 ROM 而异（本次实测本机未解绑） | ⚠️ 同上 |

**普通应用无法自行重新开启这两项授权**（`Settings.Secure` 对本应用只读，也没有任何 API 能代劳），这是 Android 的安全模型限制，不是没实现。所以 App 能做的是把这件事**变得不静默**：

1. **尽早发现** —— 三个时机互补：服务被解绑的**瞬间**（`onUnbind` / `onListenerDisconnected`，会先复查系统设置以免误报抖动）、**每 6 小时**的后台巡检（WorkManager）、**App 启动**。掉线即发一条带「去开启无障碍」按钮的高优先级通知，点通知本体直达「自动记账」页。
2. **恢复正常后自己收尾** —— 权限开回来后，回到 App 前台（或打开「自动记账」页）**立刻撤掉**那条失效提醒，不必等后台巡检。没有这份收尾，用户看到的是"自检卡全绿、告警还挂着"，会以为没修好。
3. **把设置讲清楚** —— 「自动记账」页顶部有一张四项自检卡（通知使用权 / 无障碍 / 通知权限 / 省电白名单），缺哪项就给哪项的跳转按钮，并附国产 ROM 的自启动 / 省电策略引导与「打开应用详情」入口。
4. **降低被杀概率** —— 引导加入电池优化白名单。

### 建议一次配好（尤其小米 / 华为 / OPPO / vivo）

- 应用详情 → 允许**自启动**；省电策略 → **无限制**；
- 最近任务列表里把「记一笔」**锁定**（下拉或长按卡片），避免一键清理被强停；
- **清理后台 / 更新 App 之后**回「自动记账」页确认自检清单全绿。

> **一个容易踩的坑**：自检里的「省电与后台运行」读的是**系统级电池优化白名单**
> （`PowerManager.isIgnoringBatteryOptimizations`），而 MIUI 安全中心里的「省电策略：无限制」
> 是另一套东西，两者**不一定同步**。国产 ROM 上建议两处都配一遍，
> 别只看自检这一项绿了就当保活已经配好了。

### 出问题时怎么定位

```bash
# 一行看清四项状态 + 掉了哪一项（自检每次都会打这行）
adb logcat -s JiYiBiNotify

# 例子：无障碍被系统关掉时的输出
# I JiYiBiNotify: 自动记账自检：通知使用权=true 无障碍=false 通知权限=true 省电白名单=true
# W JiYiBiNotify: 自动记账不可用，缺项=ACCESSIBILITY，已发出失效提醒

# 支付后想看识别链路：窗口切换与命中日志也在同一个 TAG
# I JiYiBiNotify: 窗口切换 [com.tencent.mm] com.tencent.mm.ui.LauncherUI
# I JiYiBiNotify: 支付页面识别命中 [规则名] 支付成功 ￥12.00 ...
```

系统侧状态可以直接查：

```bash
adb shell settings get secure enabled_accessibility_services          # 无障碍服务在不在列表里
adb shell settings get secure enabled_notification_listeners          # 通知使用权在不在
adb shell dumpsys accessibility | grep "label=记一笔"                  # 服务是否真的被系统绑定了
adb shell dumpsys deviceidle whitelist | grep jiyibi                  # 电池优化白名单
```

## 功能清单

### 核心记账
- **收支记录** —— 支出 / 收入 / 转账三种交易类型
- **分类管理** —— 自定义收支分类，支持自定义图标与颜色
- **账户管理** —— 现金、银行卡、支付宝、微信、信用卡等类型，支持设置默认收支账户
- **标签系统** —— 为交易打自定义标签，便于检索
- **周期记账** —— 按规则自动入账（WorkManager 每 15 分钟检查到期规则）
- **借贷记录** —— 应收应付的手工记录与结算

### 自动记账
见上一章。一句话版本：**通知解析 + 无障碍读屏 + AI 兜底**三条链路互补，统一落库、三层去重、横幅提醒、分类学习、未识别队列可见。

### 数据可视化
- **日历热力图** —— 按月展示每日支出强度，5 档主题色梯度
- **统计图表** —— 日 / 周 / 月 / 年多维度，分类占比、账户占比、趋势折线（**全部手写 Canvas**）
- **预算追踪** —— 月度总预算 + 分类预算，实时进度与超支提醒（本月首次打开会预置 ¥1200 总预算）
- **年度回顾** —— 年度消费总结，Canvas 出图导出分享海报（走 FileProvider）

### 数据管理
- **CSV 导出** —— 表头 `日期,类型,金额(元),账户ID,分类ID,备注`，**带 UTF-8 BOM**，Excel 直接打开不乱码
- **JSON 全量备份 / 恢复** —— 覆盖 6 张数据表，恢复前有「将覆盖当前所有数据且不可撤销」的二次确认
- **搜索** —— 关键词、日期范围、金额区间、收支类型、分类多条件组合

### 个性化
- **4 种主题** —— 薄荷清新（默认）/ 紫粉活力 / 暖阳治愈 / 莫兰迪高级，每套含浅色与深色两套配色；深色跟随系统，无独立开关
- **渐变 Hero + 毛玻璃卡片** —— 首页 / 统计 / 我的
- **动效** —— 数字滚动、进度条、列表入场（`Modifier.Node` 实现，不阻塞列表项 skip）、页面转场

```
│   ├── notify/                    # 自动记账：通知监听 / 无障碍服务 / 规则解析 / 落库 / 自检 / 通知出口
│   └── work/                      # WorkManager：周期记账轮询 + 自动记账自检
├── di/                            # Hilt 模块
├── nav/                           # 路由定义与 NavHost
└── ui/                            # 界面层，按页面分包（home / statistics / autorecord / …）
```

`core/notify/` 是自动记账的全部实现，9 个文件各司其职：解析（`PaymentNotificationParser`）、两条抓取链路（`PaymentNotificationListener` / `PaymentAccessibilityService`）、统一落库（`PaymentRecorder`）、账户匹配（`PayMethodAccountMatcher`）、自检与通知出口（`AutoRecordHealth` / `AutoRecordNotifier`）、权限探测（`NotificationAccessHelper` / `AccessibilityAccessHelper`）。

## 数据库设计

Room 当前 **version 3**，6 张表：

| 表名 | 说明 |
|---|---|
| `transactions` | 交易记录（金额以**分**存储） |
| `accounts` | 账户信息 |
| `categories` | 收支分类 |
| `budgets` | 预算设置 |
| `recurring_rules` | 周期性记账规则 |
| `debts` | 借贷记录 |

金额统一以「分」（Long）存储，通过 `centsToYuan()` / `yuanToCents()` 转换，避免浮点精度问题。

**分类学习、未识别队列、AI 配置、主题等不在 Room 里**，各自是独立的 DataStore —— 所以 JSON 备份只覆盖上面 6 张表，AI API Key 等配置天然不会被写进备份文件。

### 迁移策略（重要）

本项目**刻意不使用** `fallbackToDestructiveMigration()`：那个开关一旦生效，只要版本号提升而没配好 Migration，用户全部账目会被静默清空。

- 缺 Migration 时 Room 直接抛 `IllegalStateException`（启动失败，logcat 有明确原因）—— **坏在开发期比坏在用户手机上便宜**；
- `DatabaseModule` 会在**每个应用版本首次打开数据库前**把 `.db` 复制到 `filesDir/db_backup/`（保留最近 5 份，含 `-wal`），迁移真写错了还能捞回来；
- schema JSON 提交在 `app/schemas/`（**目前有 `2.json` / `3.json`**，没有 `1.json`），是写下一个 Migration 的唯一依据。

升版本三步走：改实体并提 `version` → 跑 `./gradlew :app:kspDebugKotlin` 生成新 schema → 对照差异写 `Migration(N-1, N)`，**用旧版 APK 造数据覆盖安装验证**。

## 本地运行

### 环境要求

- Android Studio Hedgehog (2023.1.1) 或更高
- JDK 17
- Android SDK 34（`compileSdk` / `targetSdk` 均为 34）
- 最低支持 Android 8.0（API 26）

### 构建

```bash
./gradlew assembleDebug          # debug 包
./gradlew :app:testDebugUnitTest # 单元测试（纯逻辑：解析规则、金额换算、分组、归一化…）
./gradlew assembleRelease        # release 包
```

> release 目前**复用 debug 签名**，方便覆盖安装对比、保留数据；**正式发布前必须换成自有 keystore**。

> **构建环境提示**：Android Studio 开着时，它的 Gradle 守护进程会占用项目 `.gradle/` 下的锁文件，命令行构建可能报「拒绝访问」。绕法：`./gradlew ... --project-cache-dir="$TEMP/jiyibi-gradle-cli"`，或先关掉 Studio 的构建。

### AI 兜底是可选的

不配也能用：规则链路完全不依赖 AI。要用的话在「我的 → 自动记账」里填**任意 OpenAI 兼容接口**的地址、Key 与模型名。
